### Вывод второго агента по Vertex AI Search / Agent Builder

Проверено по документации 27.08.2026: **не подходит для Layer 1/3**. Его layout-parser
расплющивает таблицы через OCR в текстовые чанки для семантического поиска, теряя
точную структуру строка/столбец — а именно она нужна для пересчёта чисел
(Charlson 19.7 vs 10.4 и т.п.). Europe PMC JATS XML с настоящими
`<table><row><cell>` для этой задачи надёжнее.

Кредит €855 остаётся применим как **опциональный бонус-слой** поверх MVP —
семантический поиск «похожие случаи confounding в других статьях» — но не как замена
основному retrieval.

### ⚠️ Уточнение к этому выводу (не отменяет его)

Вывод верен для режима, в котором Vertex AI Search применяет парсер: **chunking под
семантический поиск**. Но тот же процессор Document AI Layout Parser в режиме
**standalone-разбора** отдаёт `DocumentLayout` proto — древовидную структуру с
сохранением иерархии и таблицами, включая merged cells (см. F-06). Это два разных
режима одного инструмента, и второй структуру не теряет.

→ Практически: «Vertex AI Search не подходит» ✅ принято. «Document AI не подходит» ❌
не следует из этого. Разведено в вопрос **Q-08**.

## Что из этого действительно решает нашу задачу

Отделяя «модно» от «нужно»:

1. **Document AI Layout Parser** — единственный компонент, который бьёт точно в
   заявленный moat (вытащить appendix-таблицу целиком и без выдумок).
2. **Agent Platform** — закрывает три требования хакатона одним сервисом.
3. **`background=True` (или Cloud Run Jobs как запасной)** — превращает «прогон одной
   статьи» в «фоновый батч», то есть в формулировку темы хакатона.
4. **ADK с разделением на суб-агентов** — не украшение: документация вендора прямо
   советует так делать, а критерий архитектуры весит 30%.

Остальное — кандидаты, которые надо оправдать задачей, а не наличием в стеке.
