## D-01 · Базовая модель — `gemini-3.7-flash`

**Дата:** 2026-08-27 · **Статус:** принято

**Контекст.** Правила требуют Gemini 3.5+. На Vertex Pro-линейка обрывается на
3.1-preview (F-01). Наш валидированный результат снят на 2.5 Pro, которая запрещена.

**Решение.** Основная модель — `gemini-3.7-flash` на `global`/`v1beta1`.
`gemini-2.5-pro` остаётся в eval-харнесе как исторический бейзлайн и в подачу не идёт.

**Почему.** Единственная доступная линейка, проходящая порог. 3.7 — старшая в ней.

**Что отменит.** Появление Pro ≥3.5 на Vertex до дедлайна (перепроверить за сутки);
либо результат Q-00, показывающий, что 3.7-flash хуже 3.6/3.5 на нашей задаче.

## D-03 · Свой eval-харнес сейчас, Vertex evaluation service — потом

**Дата:** 2026-08-27 · **Статус:** принято

**Контекст.** У Vertex есть родной Gen AI evaluation service с rubric-based метриками
(F-08), но его API не подтверждён вживую. До дедлайна 4 дня.

**Решение.** Метрику качества считаем своим харнесом в `eval/`. Переход на родной
сервис — отдельной задачей, если останется время, и только как **дополнение**
(результаты обоих должны сойтись).

**Почему.** Принцип «не изобретать велосипед» здесь уступает более важному: мерить
качество надо начинать сегодня, а не после изучения чужого SDK. Харнес намеренно
тонкий (один файл), чтобы его не жалко было выбросить.

**Что отменит.** Обнаружение, что родной сервис заводится за час и покрывает нашу
метрику покрытия пунктов.

## D-04 · Строгая метрика считается только на McDonald

**Дата:** 2026-08-27 · **Статус:** принято

**Контекст.** Полноценный экспертный разбор есть ровно один (F-05).

**Решение.** Основная метрика — покрытие 5 пунктов на McDonald. По статьям 02–05
считается только слабый recall (нашёл ли агент известный сигнал) и ведётся ручной
список новых находок. В любых материалах подачи цифра качества сопровождается
указанием размера выборки.

**Почему.** Показывать «4.5/5 на корпусе из 5 статей» было бы враньём: на четырёх из
пяти сравнивать не с чем.

**Что отменит.** Достройка эталонов для 02–05 либо внешний эталонный корпус (Q-01).

## D-07 · Layer 0 строим на background execution, Cloud Run Jobs держим запасным

**Дата:** 2026-08-27 · **Статус:** принято условно (зависит от Q-10)

**Контекст.** Планировалась своя очередь на Cloud Tasks. Обнаружен `background=True`,
который сам отдаёт interaction ID и снимает reasoning loop на сервер (F-15).

**Решение.** Целимся в background execution. Своя очередь не пишется. Cloud Run Jobs
остаются запасным вариантом до ответа на Q-10.

**Почему.** Экономит день работы и лучше отвечает теме хакатона («agents that run in
the background»). Но параметр в бете и документирован на стороне Gemini API, а не
Vertex — поэтому решение условное, а не окончательное.

**Что отменит.** Отрицательный ответ на Q-10.

## D-09 · Числа берутся только из структурного парсинга, никогда из grounding

**Дата:** 2026-08-27 · **Статус:** принято

**Контекст.** `VertexAiSearchTool` отдаёт `groundingMetadata` с привязкой
предложение→источник, что почти бесплатно закрывает цитирование в Layer 6.

**Решение.** Grounding используем для цитирования **текста**. Любое число, попадающее в
отчёт, берётся **только** из структурного парсинга таблиц (JATS XML / Document AI).

**Почему.** Grounding опирается на чанки Vertex AI Search, а чанкинг расплющивает
таблицы и теряет структуру строка/столбец (F-19б). Взять число оттуда — значит
воспроизвести ровно ту ошибку, которую продукт создан ловить. Проект уже поймал такую
ошибку у себя (F-12) и знает её цену.

**Что отменит.** Ничего. Это правило уровня принципа, а не оптимизации.

## D-10 · Layer 0 строится на Cloud Run Jobs. Отменяет D-07

**Дата:** 2026-08-27 · **Статус:** принято · **Отменяет:** D-07

**Контекст.** D-07 закладывал Layer 0 на `background=True`, сняв с плана свою очередь.
Проверка (F-20) показала: механика на Vertex работает, но **исключительно для
managed-агентов** — все восемь проверенных моделей generateContent, включая нашу
`gemini-3.7-flash`, отвечают `400 Unsupported model interaction`.

**Решение.** Асинхронность Layer 0 — на **Cloud Run Jobs**. Interactions API из
архитектуры убирается.

**Почему.** Наш пайплайн — это вызовы обычной модели по слоям, а не делегирование
managed-агенту. Cloud Run Jobs при этом закрывает требование R3, официально одобрен как
хост для агентов, и всё равно был нужен: 429-ошибки (F-11) требуют очереди с ретраями
независимо от того, каким способом запускается работа.

**Что отменит.** Появление поддержки обычных моделей в Interactions API. Проверяется
одной строкой — тем же зондом, что дал F-20.

**Что при этом сохраняется из D-07.** Своя очередь по-прежнему не пишется: берём
готовый Cloud Run Jobs, а не самодельный шедулер.

## D-11 · Retrieval двухпутевой: Europe PMC для открытых, приложенный PDF для закрытых

**Дата:** 2026-08-27 · **Статус:** принято

**Контекст.** Q-02 закрыт замером (F-21…F-23): Europe PMC покрывает ~27% статей класса
и для них отдаёт всё нужное, но наша ключевая статья McDonald недоступна (0 из 3 по
собственному корпусу).

**Решение.** Два пути в Layer 1, оба обязательны:

- **Путь A — открытая статья (~27%):** DOI → Europe PMC → JATS XML (основные таблицы)
  + `supplementaryFiles` → `.docx` → `scripts/docx_tables.py` (таблицы приложения).
  Полностью автоматический, бесплатный, работает уже сейчас.
- **Путь B — закрытая статья:** пользователь прикладывает PDF → Document AI Layout
  Parser (batch, т.к. статьи обычно >15 страниц) → таблицы. Это и есть сценарий McDonald.

Развилка из STATE.md («если full-text недоступен массово — просите PDF») разрешается
не выбором одного из вариантов, а тем, что нужны оба.

**Почему.** Строить только путь A — значит не уметь разобрать собственную опорную
статью. Строить только путь B — терять автоматизм, который и есть тема хакатона.

**Что это даёт для демо.** Честный сюжет: агент сам определяет, доступна ли статья, и
переключает стратегию — это видимое поведение, а не спрятанная деталь.

**Что отменит.** Ничего в обозримом сроке: лицензионное покрытие Europe PMC от нас не
зависит.

## D-12 · Для `.docx`-приложений парсер свой, Document AI только для PDF

**Дата:** 2026-08-27 · **Статус:** принято

**Контекст.** Планировалось отдать парсинг приложений в Document AI Layout Parser
или GROBID. Замер показал: все 9 текстовых приложений в выборке — `.docx`, PDF нет
ни одного (F-22).

**Решение.** Приложения `.docx` парсим сами (`scripts/docx_tables.py`, ~60 строк,
без зависимостей). Document AI остаётся **только для пути B** — приложенных PDF.

**Почему.** Это не нарушение принципа «не изобретать велосипед», а его применение:
`.docx` уже является структурированным XML, и таблицы в нём размечены явно. Прогонять
его через OCR-парсер значило бы взять текст, у которого структура есть, разрушить её и
пытаться восстановить. Вопрос Q-08 (не расплющивает ли Document AI таблицы) для этого
пути просто перестаёт существовать.

**Что отменит.** Появление в выборке заметной доли PDF-приложений — тогда Document AI
понадобится и здесь.

## D-13 · Уровень доказательности как часть выхода, откалиброванный замером

**Дата:** 2026-08-27 · **Статус:** принято · **Автор идеи:** пользователь

**Контекст.** Автоматически достаётся ~55% статей, и достаётся неодинаково: у одних
есть приложения, у других только основной текст, у третьих один абстракт (F-25).
Попытка «дотянуть до 100%» упирается в защиту сайтов издателей и не решается в срок.

**Решение.** Не прятать разницу, а **сделать её явной частью отчёта**. Каждый разбор
выходит с уровнем доказательности, который определяется тем, что удалось достать:

| Уровень | Что достали | Доля класса | **Измеренное качество** |
|---|---|---|---|
| **L1** | full-text + таблицы приложения | 22% | **4.0–4.5 / 5** |
| **L2** | полный текст без приложений | 27% | **3.5 / 5** (F-26) |
| **L3** | только абстракт и метаданные | 50% | **3.0 / 5** |

**Почему это сильное решение, а не отговорка.** Цена каждого уровня у нас **измерена**
(F-13, F-40), а не назначена. Мы можем сказать судьям и пользователю: «на этом уровне
агент воспроизводит столько-то экспертных пунктов, и вот замер».

> ⚠️ **Поправка 28.08 (F-44).** Здесь стояло «и систематически ошибается направлением
> confounding». Проверка это **опровергла**: на абстракте направление называется верно
> в 4 прогонах из 4. Ошибка была в переобобщении — F-26 измерял ненайденный пункт
> эталона, а не неверное поле `direction`. Настоящее различие: ниже L1 обоснование
> опирается на общие свойства дизайна, а не на числа из документа, и потому непроверяемо.
> Верная догадка доказательством не является — на этом и держится потолок. Это ровно тот продукт,
который проект и декларирует: инструмент, который знает, чего он не знает.

Уровень определяет и поведение: на L3 находки помечаются как
`PLAUSIBLE-UNVERIFIED`, и отчёт прямо говорит, каких таблиц не хватило и что именно
они бы уточнили.

**Связь с Layer 5.** Это наполняет содержанием уже задуманный слой Confidence:
`CONFIRMED` достижим только на L1, на L3 честный максимум — `PLAUSIBLE-UNVERIFIED`.

**Пробел закрыт 27.08:** L2 откалиброван прогоном `20260827-190241` — **3.5/5** (F-26).
Все три уровня теперь измерены, ни один не назначен.

**Что показал замер сверх ожиданий.** Уровни не просто «хуже/лучше» — они открывают
конкретные пункты: P4 берётся ровно тогда, когда появляется Table 2; P1 и P2 — только
с приложением. И главное: **ошибка направления (P2 = 0.0) держится и на L2, не только
на L3.** То есть полный текст статьи без приложений НЕ спасает от неверного вывода —
спасает только приложение. Это усиливает тезис проекта, а не ослабляет его.

**Что отменит.** Ничего. Даже если покрытие вырастет, уровни остаются — они описывают
качество вывода, а не временное ограничение доступа.

## D-14 · Каждое число проходит обратную сверку с первоисточником, кем бы оно ни было извлечено

**Дата:** 2026-08-27 · **Статус:** принято · **Обобщает:** D-09

**Контекст.** За один день три независимых сигнала одного класса:

- **F-27** — уверенное утверждение о пакете `adk-ext[firestore]`, которого не существует.
- **F-29** — Gemini 3 Flash: **79.3%** на table understanding; «почти 100% data accuracy
  **для большинства таблиц**» — оговорка убийственная для продукта, который живёт
  редкими расхождениями в конкретных ячейках.
- **prior-art, п.4** — Docling на плотных числовых данных «hallucinates column names,
  repeats values across rows, loses track of merged cells».

Общее: **любой источник — чужой парсер, мультимодальная модель, поисковая выдача —
уверенно врёт именно на плотных числах.** Это ровно тот класс ошибки, который продукт
существует, чтобы ловить у других. Проект уже поймал такую ошибку у себя (F-12).

**Решение.** Ни одно число не попадает в отчёт без обратной сверки с первоисточником.
Правило действует независимо от способа извлечения.

**Что «сверка» значит технически** (иначе это лозунг, а не правило):

1. **Дословный поиск.** Извлечённое число ищется в исходном тексте статьи (JATS XML,
   `word/document.xml` приложения, текстовый слой PDF) как строка, с нормализацией
   разделителей (`1,234` / `1 234` / `1234`; `.` / `,` как десятичный).
2. **Не найдено → число помечается `UNVERIFIED` и не используется в расчётах.**
   Не «вероятно опечатка парсера», не «округлим» — исключается.
3. **Связка с контекстом.** Число сверяется вместе с меткой строки и столбца: «19.7»
   само по себе ничего не значит, значение имеет «Charlson ≥5, группа GLP-1, 19.7%».
   Сверяется пара, а не значение.
4. **Арифметическая перекрёстная проверка,** где данные позволяют: доли против
   абсолютных чисел, разница долей против NNT. В проекте это уже сработало —
   инверсия направления в F-12 была поймана именно арифметикой
   (1.9 п.п. × 15 264 ≈ 290).
5. **Расхождение самого первоисточника с собой — это находка, а не ошибка сверки.**
   В McDonald таких две (217 025 против 217 624; «2.60%» вместо 2.47%). Их надо
   выводить в отчёт как отдельный класс наблюдений, а не молча выбирать одно значение.

**Почему это не перестраховка.** Продукт заявляет: «модели угадывают правдоподобное
вместо верного, когда им не дали данных». Если наш собственный пайплайн пропустит
галлюцинированное число в отчёт, проект опровергает сам себя одним примером.

**Что отменит.** Ничего. Это правило уровня принципа.
