## F-11 · Vertex отдаёт 429 на серии подряд идущих вызовов

**Дата:** 2026-08-27 · **Способ:** поймано вживую при первом прогоне харнеса

Четыре вызова `gemini-3.7-flash`/`gemini-2.5-pro` подряд прошли, пятый (первый вызов
судьи) упал с `429 RESOURCE_EXHAUSTED` на `merci-prod`/`global`.

**Что сделано:** в `eval/harness.py` добавлен backoff (5 попыток, 8с → 128с) на
429/503/500, пауза `PAUSE_SEC = 6` между вызовами, изоляция ошибок судьи (падение
одного вердикта не роняет прогон) и сохранение файла после каждого вердикта.

**Следствие для архитектуры:** любой батч-прогон по корпусу обязан иметь очередь с
ретраями. Это довод за Cloud Tasks / Cloud Run Jobs, а не за самописный цикл.

## F-12 · ⚠️ Пойманная ошибка переноса: направление дисбаланса по истории рака груди

**Дата:** 2026-08-27 · **Способ:** судья харнеса поймал внутреннее противоречие эталона,
проверено по первоисточнику

При сборке `eval/ground_truth/mcdonald-2026.yaml` и входа B направление пункта P1 было
**инвертировано**: записано «GLP-1 9.2% против контроль 5.9%», тогда как в
первоисточнике — наоборот.

**Первоисточник** (`~/code/my-research/01-glp1-asco2026-research/01-исследования/РАЗБОР-первоисточник.md`, строки 46–47):

> Full set: «History of Breast Cancer = Yes»: контроль **9.2%** (8 876) vs GLP-1 **5.9%** (907).
> Matched set: контроль **7.8%** vs GLP-1 **5.9%** — даже после матчинга не уравнено.

**Арифметическая проверка:** (7.8 − 5.9) п.п. × 15 264 ≈ **290** «лишних» высокорисковых
женщин **в контроле** — сходится с формулировкой эксперта. Инвертированное чтение
арифметику не даёт.

**Почему это важно.** Ошибка инвертировала центральный пункт критики: при инверсии
дисбаланс работал бы ПРОТИВ наблюдаемого «защитного» эффекта, а не объяснял его.
Модель `gemini-2.5-pro` ответила **правильно**, а испорченный эталон снизил ей оценку
за P1 до 0.5. То есть замер наказывал за верный ответ.

**Как поймано.** Судья заметил, что числа в эталоне не согласуются со словами
«контроль обогащён» в том же эталоне. Это ровно тот класс ошибки, о котором
предупреждает `~/.claude/CLAUDE.md`: число перенесено без правила, по которому оно
применяется.

**Что исправлено:** эталон и вход B; в P1 добавлены поля `direction` и `trap`
(инверсия направления теперь ловится как ошибка). Прогон
`20260827-181155-mcdonald-2026` считается **невалидным по пункту P1** и подлежит
перезамеру.

## F-14 · Многоагентное разделение — официально рекомендуемый паттерн ADK ✅

Документация ADK прямо предупреждает, что «stuffing all tools into a single agent's
system prompt degrades reasoning quality», и советует делегировать специализированным
суб-агентам.

**Значение:** разбиение на Layer 2 (Fast Critic) / Layer 3 (Verifier) / Layer 4
(Adversarial) — не переинжиниринг под вкус судей, а рекомендация вендора. Снимает
возражение из первоначального списка открытых вопросов STATE.md.
Дополнительный вес: критерий «Architectural Discipline & Tech Stack» — 30% оценки.

## F-15 · `background=True` существует — но это **Interactions API, а не примитив ADK**, и он в бете ⚠️

**Источник:** [Google Developers Blog, «Building agents with the ADK and the new Interactions API»](https://developers.googleblog.com/building-agents-with-the-adk-and-the-new-interactions-api/), дата поста 11.12.2025.

Дословно:

> «By setting `background=True`, the API immediately returns an interaction ID and
> offloads the reasoning loop to the server.»

Также подтверждено: `previous_interaction_id` позволяет переложить ведение истории
диалога на сервер.

**Три поправки к формулировке «готовый примитив ADK»:**

1. Это **Interactions API** — единый шлюз к моделям и к managed Deep Research Agent;
   ADK с ним интегрируется, но сам параметр принадлежит не ADK.
2. Запуск описан как **beta** (11.12.2025). GA-статус не заявлен.
3. Документация, на которую ссылается пост — `ai.google.dev/gemini-api/docs/interactions`,
   то есть **Gemini API**, а не Vertex AI. Наши креденшелы и кредиты — на Vertex.
   **Доступен ли `background=True` через Vertex — не проверено.** Открыт как Q-10.

Механика полинга в посте не раскрыта («asynchronously poll the endpoint») — конкретный
метод нужно смотреть в самой документации API перед закладкой в Layer 0.

**Вывод:** направление верное, план с самописной очередью действительно можно снять —
но не раньше, чем `background=True` заработает под нашим проектом на Vertex.
До этого Cloud Run Jobs остаются запасным вариантом.

## F-16 · Firestore SessionService: существует, но **не в основном пакете ADK** ⚠️

**Что подтвердилось:** есть официальная страница интеграции
`adk.dev/integrations/firestore-session-service/`, класс `FirestoreSessionService`,
инициализируется project ID и необязательным именем коллекции (по умолчанию
`adk_sessions`), реализация транзакционная.

**Поправки:**

1. [Официальный блог Google Cloud про state и memory в ADK](https://cloud.google.com/blog/topics/developers-practitioners/remember-this-agent-state-and-memory-with-adk)
   перечисляет **только три** реализации: `InMemorySessionService`,
   `DatabaseSessionService` (SQLite/MySQL/PostgreSQL), `VertexAISessionService`.
   Firestore там **не упомянут**.
2. Firestore-версия ставится **отдельным пакетом**: `pip install 'adk-ext[firestore]'`,
   импорт `from adk.ext.sessions import FirestoreSessionService` — то есть это
   расширение, а не встроенная интеграция.
3. ⚠️ **`adk-ext` на PyPI не найден** (`pip index versions adk-ext` → «No matching
   distribution found», проверено 27.08.2026). Либо другое имя, либо другой индекс,
   либо пакет ещё не опубликован. Открыто как Q-12.

**Вывод:** «не нужна своя БД под состояние джобы» — вероятно верно, но пока не на чем
это построить. Гарантированно доступный путь на сегодня — `VertexAISessionService`
(если идём через Agent Platform) или `DatabaseSessionService`.

## F-17 · `VertexAiMemoryBankService` — подтверждён, Preview, работает вне Agent Engine ✅

**Источник:** тот же официальный блог Google Cloud.

- Точное имя класса — **`VertexAiMemoryBankService`** (не `VertexAIMemoryBankService`).
- Vertex AI Memory Bank — в статусе **Preview**.
- Механика: Gemini **извлекает ключевую информацию** из сессии и сохраняет только
  существенные воспоминания, а не сырую переписку; поиск — векторный по схожести.
- Методы: `await memory_service.add_session_to_memory(session)` и
  `await memory_bank_service.search_memory(app_name=..., user_id=..., query=...)`.
- **Важное для нас:** развёртывается и вне Agent Engine, например на Cloud Run.

**Гипотеза второго агента** (копить туда библиотеку найденных паттернов confounding,
чтобы система умнела от статьи к статье) документацией **не подтверждена и не
опровергнута** — это применение за пределами описанного сценария «память о пользователе».
Оставлено как Q-11. Отдельно отмечу риск: Memory Bank ищет по схожести и хранит
извлечённое, а не дословное — для накопления **паттернов** это годится, для хранения
**чисел из таблиц** категорически нет.

## F-40 · ⚠️⭐ Цены уровней в коде были пятибалльными числами под шестибалльным знаменателем — перемерено

**Дата:** 2026-08-28 · **Способ:** обнаружено при подготовке README, устранено тремя

слой 4 ловит у моделей как `GROUP_MISMATCH`: значение подлинное, но приписано не туда.
Числа стояли в проде, отдавались через `GET /levels` и чуть не уехали на первый экран

**Замер заново** — промпт v2 (ROBINS-E, тот, что в проде), эталон version 2,

| Прогон | абстракт | full-text без приложений | + приложения |
|---|---|---|---|
| `20260827-201852` | 4.0 | 4.5 | 5.0 |
| `20260828-100615` | 3.5 | 5.0 | 6.0 |

## F-41 · 🔴 Знаки сравнения в тексте статьи вырезались как разметка — треть источника терялась при сверке

**Дата:** 2026-08-28 · **Способ:** найдено при первом сквозном прогоне пути B;
подтверждено измерением на реальном PDF и на JATS

**Что было.** `verify_numbers.normalise` снимала разметку паттерном `<[^>]+>`.
В научном тексте «<» и «>» — это ещё и знаки сравнения: «p < 0.001 for all scales and
coefficients > 0.80». Всё между ними считалось одним тегом и вырезалось вместе с
числами.

| Источник | Длина | После «снятия разметки» | Потеряно |
|---|---|---|---|
| PDF статьи (Frontiers, 12 стр.) | 72 468 | 47 980 | **24 488 (34%)** |
| JATS того же PMC13318673 | 132 257 | 75 998 | на 2 877 больше, чем нужно |

**Последствие.** Верификатор судил по искалеченному источнику. Числа, честно
процитированные моделью из статьи — `267 consecutive patients`, `199 participants
(97.1%)` — получали статус `UNVERIFIED`. Это ровно тот отказ, который для проекта
хуже всех остальных: **обвинить в галлюцинации того, кто не галлюцинировал** (тот же
класс, что F-32 и первый случай 27.08 с eTable).

**Почему не всплыло раньше.** На пути A потери меньше (JATS плотнее размечен, знаков
сравнения в нём меньше в пропорции), и статьи проходили с `unverified: 0`. Баг стал
виден, только когда источником стал текст PDF — то есть **новый путь вскрыл дефект
старого**. На пути A он тоже был: 2 877 символов из JATS терялись зря.

**Исправление.** Тег обязан начинаться с буквы или `/`: `</?[A-Za-z][^<>]*>`.
На PDF съедает 0 символов, на JATS снимает разметку полностью (тегов не остаётся).

| Путь, статья `10.3389/fonc.2026.1742210` | до | после |
|---|---|---|
| B (PDF + DOI) | 4 `UNVERIFIED` из 64 | **0 из 61** |
| A (Europe PMC) | 0 из 56 | **0 из 80** |

**Тест:** `tests/test_normalise_math.py`. Проверен возвратом бага — падает тремя
проверками из восьми, включая сквозную. Первая редакция теста была слабой: число
`267` в примере стояло **после** закрывающего знака и уцелевало даже с багом.
Проверять надо число **между** знаками — это и есть вырезаемый кусок.

**Правило:** тест, написанный на исправленный код, обязан быть проверен возвратом
дефекта — второй раз за проект (первый: F-38, где параллельный тест не поймал гонку).

- **P1 взят с правильным направлением.** Модель нашла дисбаланс истории рака груди в

  утверждая «healthy user effect» (F-26). **На живом файле с приложением ошибка не
  повторилась.**
- **Классификация совпала с экспертной дословно:**
  `real_association_explained_by_selection` против «реальная ассоциация, объяснимая

- Уровень L1, 38 чисел проверено, **0 невалидных**, 35 секунд.

**Следствие для заявки:** в описание идёт цифра с живого PDF, а не с реконструкции.
Завышать нельзя — тем более проекту, который создан ловить завышение у других.

**Оговорка про UNVERIFIED — известное ограничение метода.** В прогоне 3 два таких
статуса пришлись на одно значение: модель написала «over the short 3.5-year window

Ветка `computed` из сверки исключена (D-14), но здесь вычисленное значение попало в
текстовое обоснование, а не в неё. Честная классификация требовала бы третьего статуса

оставлено как есть и записано ограничением, а не выдано за точность.

## F-44 · 🔴 Опровергнуто собственное утверждение: на L3 модель НЕ ошибается направлением

**Дата:** 2026-08-28 · **Способ:** 4 прогона на живом абстракте McDonald (1 через
задеплоенный сервис, 3 локально), промпт ROBINS-E, temperature 0

**Что утверждал продукт.** В отчёте на уровнях L2/L3 выводилась строка:

> «По замеру проекта на этом уровне модель систематически ошибается направлением
> confounding — ни одна находка не может считаться подтверждённой».

**Что показала проверка.** Все четыре прогона по одному только DOI:

| Прогон | `overall.direction` | `confounding.direction` | classification |
|---|---|---|---|
| живой сервис | `away_from_null` | `away_from_null` | `real_association_explained_by_selection` |
| локальный 1 | `away_from_null` | `away_from_null` | то же |
| локальный 2 | `away_from_null` | `away_from_null` | то же |
| локальный 3 | `away_from_null` | `away_from_null` | то же |

**Направление верное во всех четырёх.** Утверждение неверно.

**Откуда взялась ошибка — она моя, а не модели.** В F-26 измерялось, что пункт эталона
**P2 («GLP-1-группа больнее, но рака меньше») не берётся** на абстракте и на полном
тексте. Отсюда я вывел, что «модель ошибается направлением confounding». Это
**переобобщение**: ненайденный пункт эталона и неверное значение поля `direction` — не
одно и то же. Причём измерялось это на промпте v1, а в проде работает ROBINS-E, который
требует называть направление для каждого домена явно.

**В чём различие L3 и L1 на самом деле** — видно из обоснований:

| Уровень | Чем модель обосновывает направление |
|---|---|
| L3 | «GLP-1 users often receive closer clinical monitoring or possess unmeasured health-seeking behaviors»; «matching omitted parity, age at menarche…» — рассуждения, подходящие **любой** наблюдательной работе |
| L1 | «Matched non-users had a prior breast cancer prevalence of 7.8% (1,197/15,264) vs 5.9% (907/15,264) — Table A2» — конкретное число **из этого документа** |

То есть на абстракте модель **угадывает направление правильно, но без доказательства**.
Обоснование не привязано к статье и не проверяемо; сверять там нечего, потому что
цитировать нечего.

**Это обосновывает потолок `CONFIRMED` лучше прежнего утверждения**, а не хуже:
подтверждённой находка вправе называться, только если под ней лежит проверяемое число
из документа, а не правдоподобное рассуждение. Правильность догадки не делает её
доказательством.

**Что исправлено:** формулировка `caveat` в `pipeline.run`, README, текст заявки и
`docs/07-architecture.md`. Прежняя формулировка держалась на моей интерпретации, не на
замере, — и три дня стояла в продукте.

**Правило:** утверждение, которое продукт показывает пользователю, обязано иметь
собственный замер. Замер соседнего свойства и вывод «значит, и это тоже» — не замер.

## F-45 · ⭐ Суб-агент на сопоставимость групп: 3.5 → 5.5 из 6 на живой статье

**Дата:** 2026-08-28 · **Способ:** 3 прогона до и 3 после, один и тот же PDF McDonald,
один и тот же судья и эталон version 2

**Гипотеза, которую проверяли.** Пункт P2 («GLP-1-группа больнее — Charlson 5+ 19.7%
против 10.4%, — а рака у неё меньше») не брался на живом PDF **ни разу из трёх** (F-43),
хотя на подготовленном входе брался на 1.0. Предполагалось, что дело не в способности
рассуждать, а в конкуренции задач внутри одного вызова: искать факты по семи доменам и
одновременно складывать из далеко стоящих чисел противоречие.

**Что сделано.** Второй проход по тому же документу — `truth/subagents.py`,
`prompt_baseline_table.md`. Одна задача: таблица базовых характеристик. Процедура из
четырёх шагов, где третий — тест на противоречие: перечислить все характеристики, по
которым экспонированная группа стартует хуже, и сверить с заявленным результатом.
Идёт **параллельно** основному критику (оба смотрят в один документ под разными углами),
результат вливается в домен Confounding.

| | прогон 1 | прогон 2 | прогон 3 | медиана |
|---|---|---|---|---|
| один критик (F-43) | 3.5 | 3.5 | 4.5 | **3.5** |
| + суб-агент | 5.5 | 6.0 | 5.0 | **5.5** |

**P2 = 1.0 во всех трёх прогонах** (было 0.0 во всех трёх). Суб-агент выдал ровно те
числа, которых не хватало: `Charlson Risk Score 5+ very high: GLP-1 3,008 (19.7%) vs
No GLP-1 10,005 (10.4%) [Appendix Table A1]`. Заодно поднялся P4 — он нашёл диабет
53.4% против 17.6%.

**Промпт правился дважды, и оба раза по существу, а не под тест:**

1. **`favours: unclear` у коморбидности.** Первая версия извлекала Charlson, сердечную
   и почечную недостаточность, но помечала их «unclear» — то есть пропускала шаг 2, и
   шаг 3 работать уже не мог. Добавлено: «unclear» — для характеристик, чьё влияние на
   исход в медицине действительно спорно, а не для тех, о которых не подумали.
2. **Молчаливый выбор matched-набора.** Модель брала только matched (19.7% против 17.3%),
   где дисбаланс слабее, хотя в полном наборе он драматичен (19.7% против 10.4%).
   Добавлено требование давать оба набора: разница между ними сама по себе показывает,
   сколько дисбаланса матчинг снял, а сколько оставил.

**Правило отбора задач для суб-агента** (записано в докстринге `subagents.py`): задача
механическая и описывается по шагам; внутри общего промпта измеримо проваливается; её
результат проверяем — состоит из чисел, которые верификатор сверит с документом.
Остальные шесть доменов ROBINS-E этому не отвечают, и суб-агентов для них нет.

**Расхождение не сводится молча.** Если суб-агент и основной критик дают разное
направление домена, в отчёт попадает поле `disagreement` с обоими значениями. Свести их
в одно означало бы выдать за факт то, что на деле спорно.

**Побочно исправлено:** числа с ведущей точкой. В статьях сплошь «P < .0001», а regex
выдёргивал из этого «0001», которого в тексте отдельным числом нет, — и модель получала
`UNVERIFIED` за точную цитату. Третий случай ложного обвинения за проект (после F-41 и
приложений 27.08).

**Цена:** второй вызов модели на статью, +~35 секунд параллельно (общее время не
выросло), число проверяемых чисел выросло с ~40 до ~400 — суб-агент выдаёт всю таблицу
характеристик, и каждое её число идёт в сверку.

## F-47 · 🔴 Второй эталон, внешний: 1.0 из 4. Калибровка на одном кейсе завышала оценку

**Дата:** 2026-08-28 · **Способ:** 3 прогона пути A на статье, которой система раньше

**Откуда взялся эталон — и почему он честнее первого.** Q-01 ставил вопрос: вся
калибровка стоит на одном кейсе, разобранном самим автором проекта. Возражение
«эталон и система сделаны одной головой» снимается только внешним источником.

Найдено опубликованное письмо в редакцию: **Fei Lu, «Time-Related Biases in
Observational Studies of GLP-1 Agonists and Cancer Risk»**, Journal of Diabetes,
`10.1111/1753-0407.70202` (PMC12967869) — с ответом авторов (`...70203`). Критика
адресована статье **Cheng et al., `10.1111/1753-0407.70013`** (PMC11494487), которая
лежит в Europe PMC с приложением, то есть берётся нашим путём A на уровне L1.

Пункты эталона не сочинены нами — они перенесены из письма
(`eval/ground_truth/cheng-2024.yaml`, четыре пункта).

**Результат:**

| Кейс | Эталон | Прогоны | Медиана | Доля |
|---|---|---|---|---|
| McDonald (наш разбор) | 6 пунктов | 5.5 · 6.0 · 5.0 | 5.5 | **92%** |
| Cheng (внешнее письмо) | 4 пункта | 1.5 · 1.0 · 1.0 | **1.0** | **25%** |

**Разбор по пунктам (устойчиво во всех трёх прогонах):**

| Пункт | Балл | О чём |
|---|---|---|
| C1 predominant-user, нет washout | 0.5 | берётся частично |
| C2 нет lag-периода → detection bias | 0.5 | берётся частично |
| C3 градиент по длительности обратный причинному | **0.0** | не берётся |
| C4 наблюдение ~24 мес короче латентности | **0.0** | не берётся |

**Что это значит.** Система заточена под класс дефектов первого кейса — конфаундинг и
сопоставимость групп, — и там работает хорошо. Второй кейс о другом: **time-related
biases** (prevalent-user, lag period, градиент по длительности, латентность). Это
отдельный, признанный класс фармакоэпидемиологических ошибок, и наш промпт ROBINS-E
покрывает его слабо: `Measurement of the exposure` вбирает prevalent-user, а lag,
латентность и форму дозозависимости — нет.

**Вывод для заявки:** 92% на своём кейсе и 25% на чужом — это и есть настоящая мера
обобщаемости, и в описание идёт она, а не первая цифра. Один эталон измерял не столько
систему, сколько совпадение системы с собственным разбором её автора.

**Метод, которым это чинится, уже проверен** (F-45): найти замером устойчивый провал,
завести узкого суб-агента, перемерить. Для baseline-сопоставимости это дало +2 балла.
Тот же ход напрашивается для time-related biases — но пока он не сделан, цифра 25%
стоит как есть.

**Побочно исправлен четвёртый случай ложного обвинения.** Числа из приложения не
доходили до сверки: `_supplementary_text` заменяет XML-теги пробелами, а Word разбивает
число на несколько `<w:t>`-фрагментов — «3.04» становится «3 . 04» и не находится.
Разобранные таблицы склеивают ячейку правильно, поэтому теперь источником для сверки
служит текст статьи **плюс** разобранные таблицы. Непроверенных чисел стало 3 и 0
вместо 45.
