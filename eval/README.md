# Eval-харнес

Отвечает на один вопрос: **насколько модель самостоятельно воспроизводит экспертный
методологический разбор, и что даёт добавление таблиц приложения.**

Это исследовательский инструмент, не часть продукта — в подачу на хакатон он не идёт,
но именно он решает, есть ли что подавать (решение D-03).

## Устройство

```
ground_truth/<case>.yaml            эталонный разбор: пункты, ключевые числа, ловушки
inputs/<case>.abstract.md           вход A — только уровень абстракта
inputs/<case>.with_appendix.md      вход B — то же + таблицы приложения
prompts/critic_vN.md                промпт критика (одинаков для A и B)
results/<timestamp>-<case>.json     прогон: сырой ответ, разбор, вердикт судьи, счёт
harness.py                          прогон + скоринг + отчёт
```

**Единственная переменная эксперимента — вход A против входа B.** Промпт, модель,
температура (0) и всё остальное совпадают. Если менять что-то ещё, прогон перестаёт
отвечать на вопрос про retrieval.

## Запуск

```bash
bash scripts/preflight.sh          # сначала всегда

# основной эксперимент: одна модель, два входа
python3 eval/harness.py run --models gemini-3.7-flash

# сравнение с историческим бейзлайном (2.5 Pro в подачу не идёт — только ориентир)
python3 eval/harness.py run --models gemini-3.7-flash,gemini-3.5-flash,gemini-2.5-pro

python3 eval/harness.py report     # таблица по всем прогонам
```

## Как считается счёт

Судья-модель сравнивает находки аудитора с эталонными пунктами и ставит по каждому
1.0 / 0.5 / 0.0. Шкала выбрана так, чтобы результат был сопоставим с исторической
записью «3.5/5 → 4.5/5».

Два жёстких правила судьи:

1. **Ловушка важнее полноты.** Если у эталонного пункта задано поле `trap` (для P2 это
   «healthy user effect») и аудитор утверждает именно её — ставится **0.0, а не 0.5**.
   Правдоподобный, но неверный по направлению вывод хуже молчания: он выглядит
   убедительно и потому опаснее.
2. **Учебниковое название без привязки к данным** — максимум 0.5. Назвать
   «confounding by indication» умеет любая модель; ценность в том, чтобы показать
   направление конкретными числами из входа.

Отдельно судья собирает находки, которых нет в эталоне, и помечает, валидны ли они —
это не штраф, а потенциальный самостоятельный улов (в раунде 1 на 2.5 Pro такой был).

## Что этот харнес НЕ доказывает

- **Строгая метрика есть только для McDonald.** Развёрнутый экспертный разбор в проекте
  ровно один (F-05, решение D-04). По остальным статьям корпуса возможна лишь слабая
  проверка «нашёл ли известный сигнал».
- **Входы — реконструкция.** Оригинальные тексты сессии 27.08, на которых получены
  3.5/5 и 4.5/5, не сохранены. Файлы `inputs/` собраны из `studies/01-mcdonald-*.md`.
  Поэтому историческая цифра **не сравнима напрямую**: чтобы сравнивать, надо переснять
  и 2.5 Pro этим же харнесом.
- ~~**Судья той же семьи, что и подсудимый.**~~ **Измерено 29.08 — опасение не
  подтвердилось.** Возражение стояло здесь с 27.08 как слова, и все числа продукта
  получены одним судьёй `gemini-3.7-flash`, той же моделью, что писала разбор.
  `eval/second_judge.py` пересуживает уже сохранённые прогоны **другой** моделью
  (`gemini-2.5-pro`); пайплайн не запускается заново — судья видит только текст
  разбора, поэтому пересчёт корректен и стоит одного вызова на прогон.

  Шесть прогонов, 32 пункта эталона: **совпадение по пунктам 29 из 32 = 91%**,
  средняя разница по пункту 0.05 балла. Считается именно по пунктам, а не по
  сумме: две модели могут сойтись в итоге, разойдясь во всех слагаемых.

  Направление смещения важнее самого совпадения. Второй судья ставит **выше**:
  медиана +0.25, диапазон 0.0…+0.5, ни одного прогона вниз. То есть свой судья
  оказался **строже** чужого — а self-preference предсказывает обратное. Итог:
  `eval/results/second-judge-gemini-2.5-pro.json`.
- **Один прогон — не замер.** Температура 0 не гарантирует детерминизма. Прежде чем
  делать вывод о разнице между моделями, гонять каждую конфигурацию ≥3 раза.

## Правила работы с результатами

- Файлы в `results/` **не перезаписываются и не удаляются** — каждый прогон новый файл.
- Цифра из прогона попадает в документы проекта только вместе с `run_id`.
- Число, попавшее в текст подачи, должно быть скопировано из файла результата,
  а не восстановлено по памяти.
